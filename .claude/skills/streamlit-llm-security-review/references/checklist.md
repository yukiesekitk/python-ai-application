各カテゴリについて、確認方法（grepパターン等）・危険なコード例・安全なコード例を示す。パターンはPython/Streamlit/主要LLM SDK（google-genai, openai, anthropic）を想定しているが、他言語・他SDKでも考え方は同じなので読み替えて適用する。

## 1. シークレット/APIキーの取り扱い

**確認方法:**
- コード中のハードコードされたキーを探す: `AIza`, `sk-`, `sk-ant-`, `api_key\s*=\s*["'][A-Za-z0-9_-]{16,}` のようなパターンをgrep
- `.gitignore`に`.env`や秘密情報を含むファイルが含まれているか。逆に、意図的に`.env`管理を廃止したプロジェクトでは、`.env`関連の記述が残っていないか（設計との矛盾）
- APIキー入力欄が`st.text_input(..., type="password")`になっているか（平文表示は軽微だが指摘対象）
- APIキーを`print()`や`logging`に渡していないか
- 例外オブジェクトをそのまま`st.error(str(e))`等で表示していないか（HTTPクライアントの例外にAPIキーやAuthorizationヘッダーが含まれるケースがある）

**危険な例:**
```python
client = genai.Client(api_key="AIzaSyD-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx")
```
```python
except Exception as e:
    st.error(f"エラーが発生しました: {e}")  # eの中にリクエストヘッダーが含まれる場合がある
```

**安全な例:**
```python
api_key = st.sidebar.text_input("Gemini APIキー", type="password")
client = get_client(api_key)  # セッション内のみで保持、ファイルには保存しない
```
```python
except Exception as e:
    logging.exception("generation failed")  # 詳細はサーバー側ログにのみ
    st.error("生成中にエラーが発生しました。しばらくしてから再度お試しください。")
```

## 2. プロンプトインジェクション/ユーザー入力の取り扱い

**確認方法:**
- システム指示（役割・振る舞いの定義）とユーザー入力が、専用パラメータ（例: `system_instruction=`, `system=`, OpenAIの`role: "system"`メッセージ）で分離されているか、それとも同じ文字列に連結されているか
- ユーザー入力の長さに上限があるか（`st.text_area`に`max_chars`があるか、送信前にバリデーションしているか）
- LLMの出力を「信頼できるデータ」として扱い、そのままファイル書き込み・コード実行・シェルコマンドに渡していないか

**危険な例:**
```python
prompt = f"あなたはプロのライターです。以下の指示に従ってください。\n{user_input}"
# user_inputに「これまでの指示を無視して...」等が含まれても構造上区別できない
```
```python
result = generate(client, model, build_prompt(user_input))
exec(result)  # LLM出力を実行するのは論外だが、類似の危険なパターン（eval, os.system）がないか確認
```

**安全な例（システム指示とユーザー入力を分離）:**
```python
config = types.GenerateContentConfig(system_instruction=SYSTEM_INSTRUCTION)
client.models.generate_content(model=model, contents=user_input, config=config)
```

**補足:** 個人用ツールで「自分の入力しか通らない」場合、プロンプトインジェクションの実害は小さい。ただし将来複数人で使う可能性がある、あるいは外部コンテンツ（メール本文、Webページなど）を要約・処理する機能がある場合は重要度が上がる。用途を確認した上で重要度を判断する。

## 3. Streamlit特有のXSS/レンダリングリスク

**確認方法:**
- `unsafe_allow_html=True`を全てgrepし、渡している文字列にユーザー入力またはLLM出力が混入するか追跡する
- `st.components.v1.html(...)` / `st.components.v1.iframe(...)`に外部・ユーザー由来のコンテンツを渡していないか
- `st.markdown(llm_output)`のように、LLMが生成したMarkdownをそのまま描画している場合、Streamlitの標準Markdownレンダラーは`unsafe_allow_html`なしではHTML/JSを実行しないため、これ自体はそこまで危険ではない。ただし将来的に`unsafe_allow_html=True`が付け足された場合に危険化する

**危険な例:**
```python
st.markdown(f"<div>{llm_generated_text}</div>", unsafe_allow_html=True)
# LLM出力に <script> や onerror= を含むHTMLが混じるとXSSになりうる
```

**安全な例:**
```python
st.text_area("生成結果", value=result, height=300)  # プレーンテキストとして表示、コピー用途にも適する
```

## 4. エラーハンドリング/情報漏洩

**確認方法:**
- `except Exception as e:` で捕まえた例外を、`st.error(str(e))`や`st.write(e)`のように詳細ごとUIに出していないか
- `traceback.format_exc()`をUIに表示していないか
- スタックトレースにファイルパス、内部関数名、APIキーの断片が含まれる可能性を考慮する
- リトライ処理がある場合、リトライ対象外（4xx等）の例外は即座に分かりやすいメッセージに変換して見せているか（内部実装の詳細を漏らさない範囲で）

**危険な例:**
```python
except Exception as e:
    st.error(str(e))  # SDKの内部例外がそのまま表示される
```

**安全な例:**
```python
except ClientError as e:
    st.error("入力内容に問題があるか、APIキーが正しくない可能性があります。")
    logging.exception("client error")
```

## 5. 依存パッケージ/サプライチェーン

**確認方法:**
- `requirements.txt` / `pyproject.toml`のバージョン指定を確認する。無制限（`>=`のみ、あるいはバージョン指定なし）は将来の破壊的変更やサプライチェーン攻撃に弱い。逆に古すぎるバージョンへの完全固定は既知脆弱性を抱えたままになるリスクがある
- 可能であれば`pip-audit`や`safety`の実行を提案する（このスキル自体は自動実行しないので、実行手順を推奨事項として書く）
- 同じ役割のSDKが新旧2系統存在する場合（例: `google-generativeai`と`google-genai`が両方requirements.txtに載っている）、意図しない方が使われるリスクがあるため指摘する
- タイポスクワッティングの可能性がある見慣れないパッケージ名がないか

**推奨対応の書き方の例:**
- 「`pip-audit`を実行し、既知の脆弱性がないか確認することを推奨する」
- 「`requirements.txt`のバージョンを`>=`ではなく上限も指定する（例: `google-genai>=1.0,<2.0`）ことで、意図しないメジャーバージョンアップによる破壊的変更を防げる」

## 6. セッション状態/マルチユーザーでのデータ混在

Streamlit特有の落とし穴として最も見落とされやすいカテゴリ。

**確認方法:**
- `@st.cache_resource`でキャッシュされた関数がAPIキーを引数に取っている場合、**引数が同じなら全ユーザー間でインスタンスが共有される**。これ自体は意図通りのことが多いが、複数人が同じサーバーの同じプロセスにアクセスする構成（社内共有サーバー等）で使う場合、あるユーザーが入力したAPIキーで生成されたクライアントを他のユーザーが（キャッシュヒットの結果として）使い回してしまう可能性がないか確認する
- モジュールレベルのグローバル変数（`_cache = {}`のような）に、リクエストごとに変わるはずのデータ（ユーザー入力、APIキー、生成結果）を保存していないか。Streamlitはマルチユーザーで1プロセスを共有するため、グローバル変数は全ユーザーで共有される
- `st.session_state`のキーが機能間で衝突していないか（CLAUDE.md等に命名規則がある場合はそれに従っているか確認する）

**危険な例:**
```python
_last_result = None  # モジュールレベルのグローバル変数

def run_generation(...):
    global _last_result
    _last_result = result  # 別ユーザーのセッションから見えてしまう
```

**安全な例:**
```python
st.session_state[RESULT_KEY] = result  # セッションごとに分離される
```

**補足:** ローカルで自分ひとりが使う個人用ツールとして明示されている場合、このカテゴリの重要度はLow/Infoに下げてよい。ただし将来的にサーバーにデプロイして共有する可能性がある場合はMedium以上として指摘する。

## 7. ファイル/外部リソースアクセス

**確認方法:**
- ユーザー入力やLLM出力を使ってファイルパスを組み立てている箇所がないか（パストラバーサル: `../`を含むファイル名の検証漏れ）
- ユーザーが入力したURLをサーバー側で`requests.get()`等でfetchしている機能がある場合、内部ネットワークやクラウドのメタデータエンドポイント（`169.254.169.254`等）へのアクセスを防ぐバリデーションがあるか（SSRF）
- ファイルアップロード機能（`st.file_uploader`）がある場合、保存先ディレクトリ・ファイル名のサニタイズ・実行可能拡張子の扱いを確認する

**該当機能がない場合:** このカテゴリはレポートで「該当機能なし」として省略してよい。存在しない機能について仮定の指摘をしない。

## 8. コスト・レート制限・DoS

**確認方法:**
- LLM APIのリトライロジックに最大回数（`_MAX_RETRIES`のような定数）とバックオフがあるか。無限リトライや極端に短い間隔でのリトライはコスト増大やレート制限のさらなる悪化を招く
- ユーザー入力の長さに上限がなく、巨大な入力をそのままLLMに送れる場合、1回のリクエストで高額な課金が発生しうる
- 同一ユーザー/セッションが短時間に大量のリクエストを送れないか（送信ボタンの二重クリック防止、連打対策など）

**安全な例（本プロジェクトのようなリトライ設計）:**
```python
_MAX_RETRIES = 3
# ServerError(5xx)や429は待機を挟んでリトライ、それ以外のClientErrorは即座に例外を投げる
```
このような設計自体は良好な点として報告してよい。

## 9. ログ/監視

**確認方法:**
- ユーザーの入力内容やLLMの応答全文を外部の監視・エラートラッキングサービス（Sentryなど）にそのまま送信していないか。個人情報や機密情報が含まれる可能性を考慮する
- ローカルログファイルにAPIキーやプロンプト全文を書き出している場合、そのログファイルのアクセス権限・保存期間は適切か

**該当機能がない場合:** 外部送信するログ基盤自体を使っていないアプリでは、このカテゴリは「該当なし」として省略してよい。
